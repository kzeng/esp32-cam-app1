## 设计决定

| 决定 | 原因／影响 |
| --- | --- |
| 默认 AI Thinker ESP32-CAM / OV2640 引脚 | 常见板型，但用户尚未确认具体厂商，列为烧录前检查项 |
| 只支持 JPEG 和三档分辨率 | 先把看图链路和控制做小；不预设高清流畅性能 |
| ESP32 提供单张图片，Ubuntu 组装 MJPEG | 集中管理超时、多观看者、拍照和重连 |
| 单进程共享采集 | 避免每个手机重复拉取，限制最多 6 路连接 |
| 无观看者时后台 2 FPS，有观看者时恢复 `TARGET_FPS` | 第二阶段需要持续检测；两种用途仍共享唯一采集线程 |
| Python / Flask / Requests / Gunicorn | Ubuntu 22.04 的 Python 3.10 可用，部署简单，无前端构建链 |
| 页面以画面为中心 | 蓝灰底色、白色控件区、深色取景区；手机上按钮和画质控件便于点按 |
| 不使用第三方 CDN、演示视频或假在线数据 | 页面资源本地提供，状态根据真实采集结果显示 |
| 网关由启动脚本监听 `0.0.0.0:8080`，frpc 映射本机 8080 | 固定入口由 kzeng 的 frps + nginx HTTPS 承接 |
| 双层访问控制 | 网页会话密码 + 摄像头局域网访问密钥；事件图片不由 nginx 静态暴露 |
| 手动照片由浏览器保存，事件图片由 Ubuntu 私有保存 | 区分用户主动下载与后台事件证据 |
| 传统背景差分优先于 AI | 2 FPS / 160×120 的 CPU 成本低且可解释；宠物识别留到第三阶段 |
| SQLite 元数据 + JPEG 文件 | 查询和事务可靠，图片无需塞进数据库；适合单机一个 worker |
| 2/3 帧确认 + 15 秒静默合并 | 过滤单帧噪声，避免连续活动产生事件风暴 |
| 三张代表图 | 触发前、首次触发、变化峰值兼顾上下文与磁盘占用 |
| 30 天且 2 GB | 双重边界，按最旧完整事件清理，避免孤儿记录／图片 |

## 第一阶段开发步骤与产物（历史记录）

### 步骤 1：检查初始目录与约束

初始项目目录为空，未发现本地 Git 仓库或项目级 AGENTS.md。只读取环境中 PlatformIO 版本信息，没有执行 `pio run`。远端分支查询没有返回已有引用，后续以实际 Git 推送结果为准。

### 步骤 2：查阅官方接口

查阅乐鑫 Arduino 2.0.17 CameraWebServer、AI Thinker 引脚表、PlatformIO `esp32cam`、Flask 流式响应等资料。引用放在对应文档中。没有把其他项目的 ESP32-S3 引脚套用于本板。

### 步骤 3：建立忽略规则与本地配置模板

创建 `.gitignore`，排除 `secrets.h`、`.env`、`.pio`、虚拟环境、缓存、日志、照片等。保留 `secrets.example.h` 和 `.env.example`，其中只有占位符。

### 步骤 4：编写板端固件

`firmware/src/main.cpp`：初始化 PSRAM / 摄像头、默认 VGA、关闭板载闪光灯、配置 Wi-Fi 自动重连、注册 `/capture`、`/status`、`/control`。接口密钥验证，配置缺失时不运行。网络栈初始化在 HTTP 服务启动之前；不关闭 brownout 检测。

`firmware/platformio.ini`：固定 espressif32 6.10.0、AI Thinker board、串口波特率和上传速度。固件无密码时允许构建，实际运行要求完成本地配置。

### 步骤 5：编写 Ubuntu 网关

`gateway/camera.py`：单采集线程、连接超时、JPEG 长度限制、最新帧新鲜度判断、共享观看者、失败退避、分辨率控制。访问摄像头时不继承主机的 HTTP 代理环境变量，避免家庭视频意外经系统代理转发。

`gateway/app.py`：配置校验、访问密码验证、12 小时签名会话、CSRF、登录频率限制、HTTP 安全头、MJPEG API、拍照下载和状态接口。`/healthz` 明确只代表网关存活。

### 步骤 6：编写手机页面

`gateway/templates/` 与 `gateway/static/`：登录、实时观看／暂停、三档分辨率、拍照后下载、全屏、连接异常提示和后台暂停。只展示实际画面，不填入示例宠物图片。手机拍照后提供明确下载链接，以兼容禁止异步自动下载的浏览器。

### 步骤 7：准备部署与操作文档

创建 systemd 模板，使用专用低权限用户、固定路径、一个 Gunicorn worker、16 线程；当前外网链路使用 frpc、kzeng/frps 和 nginx HTTPS。

### 步骤 8：交付状态与后续

第一阶段初始交付时，源码与文档写入仓库后只做文件内容和 Git 提交范围检查；当时没有执行编译、Python 服务、浏览器运行、单元测试、烧录或硬件测试。后续第一阶段已完成部分实机验证，第二阶段 2A 的软件测试结果见本文末尾；真实场景仍以 [验收清单](ACCEPTANCE.md) 为准。

本地 Git 初始化后，环境对 `.git` 写入施加限制，分支改名及远端配置失败。已连接的 GitHub 工具确认远端为空且当前账号有 push 权限；交付改由 GitHub API 提交源码，保留本地文件，不修改保护规则。本地仓库元数据因此不等同于远端历史；后续在 Ubuntu 重新 clone。

Git 提交／推送的成功与否以交付消息及远端引用为准；本文件不预先声称推送已完成。

- 不向聊天、提交、日志或 issue 粘贴实际 Wi-Fi 密码、摄像头密钥、会话密钥或 frp token。

## 第二阶段 2A 实施记录（2026-10-25）

### 范围冻结

- 本阶段实现移动检测、事件合并、三张留图、SQLite 索引、自动清理、事件页面、ROI 与阈值设置。
- 本阶段不实现外部通知、视频录像或 AI 分类；通知属于 2B，待实景误报稳定后再选渠道。
- 推荐默认参数：VGA、后台 2 FPS、连续 3 帧中 2 帧命中、15 秒静默结束、30 天、2 GB。

### 采集与检测

- `camera.py` 增加后台检测需求，不把检测器计入浏览器观看人数。无人观看时使用 `MOTION_FPS`，有人观看时使用 `TARGET_FPS`。
- `motion.py` 解码 JPEG，缩小至 160×120 灰度图，进行高斯模糊、背景差分、开运算和膨胀；只统计 ROI 内变化比例。
- 全局变化比例超过 70% 且差分较均匀时按灯光切换处理，快速适配背景且不触发事件。
- ROI 使用 0～1 百分比坐标，页面支持在当前摄像头照片上拖画；设置改变后清空旧背景和判定窗口。

### 事件与存储

- `events.py` 管理 SQLite `events`、`images`、`settings` 表；数据库启用 WAL 和外键。
- 事件确认前在内存保存约 3 秒 JPEG 环形缓冲；开始事件时落盘 `pre.jpg`、`trigger.jpg`、`peak.jpg`，后续更高变化分数原子替换峰值图。
- 图片先写 `.tmp`、刷新并 `fsync`，再 `os.replace`；数据库只引用成功写入的相对路径。
- 清理按完整事件执行：先删除超过保存天数的事件，再按最旧顺序把总图片量压到配额内。
- 摄像头连续异常约 30 秒写一次 `camera_offline`；恢复首帧写一次 `camera_recovered`。

### Web 与安全

- 新增 `/events`、`/motion` 页面及事件图片、标记、删除、检测设置接口。
- 所有事件页面和图片要求已登录；修改和删除操作要求 CSRF。事件目录不交给 nginx 静态服务。
- 首页增加今日事件数和最近活动；事件页支持全部、今天、最近 7 天、未查看筛选，每页最多 20 条。
- CSS、JavaScript 和 SVG 使用带版本号的长期缓存；HTML、状态 API 和实时流仍禁止缓存。事件图使用短期私有缓存和 ETag。
- 列表只读取峰值缩略图，展开详情时才请求三张原图。单项和批量确认／删除均用 AJAX 原地更新，不整页刷新。
- `POST /api/events/batch` 单次最多处理 100 个去重后的事件 ID；删除先将图片目录原子移动到私有 `.trash`，数据库提交后异步清理，重复请求按幂等成功处理。
- 公网 nginx 对页面和 API 做每 IP 限速与连接保护，超额返回 429；静态资源与事件图片按 URI 豁免，不能让入口保护阻塞 CSS、JavaScript 和首屏缩略图。
- systemd 继续限制为一个 Gunicorn worker，并仅给 `/opt/pet-watch/gateway/data` 增加写权限。

### 已完成验证

- Python 语法编译通过。
- 事件生命周期、缩略图、分页、批量确认／删除、幂等重试、缓存策略、设置持久化、过期清理、状态事件、局部移动、全局亮度变化、ROI 排除、鉴权、CSRF 和页面渲染均有自动测试。
- 自动测试只证明软件逻辑；真实摄像头下的误报率、阈值、功耗、温升和长期稳定性仍按验收清单执行。
